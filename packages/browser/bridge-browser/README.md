# DSH Stride Browser Bridge

English | [中文](README.zh.md)

`@eilyeee/dsh-browser-stride`
The bridge mounts a loopback-only, token-authenticated WebSocket on the local DeepSeek Harness Host and registers structured browser tools with optional Chrome viewport images. The browser extension performs the actual page operations. See the [repository README](../../../README.md) for setup and current limitations.

## Viewport images

`browser_screenshot` validates a bounded JPEG from the confirmed extension, admits it through the Host attachment service and renders a native image block. PTC attaches successful image content on the next model step. Canonical values expose only the durable attachment reference and screenshot metadata. `browser_click_at` is a normal approved write with a single-use screenshot ref and normalized image fractions; it retains the existing request, document, session and run/control fences. Both tools require the negotiated optional `visualViewport` capability. DOM snapshots remain text; native CDP input is not implemented. See the [Chrome visual-tool instructions](../../../extensions/dsh-browser/README.md#canvas-and-design-pages).

## Reading design style fields

After selecting a layer, `browser_read_design_styles` extracts explicitly labelled English/Chinese inspector values into fixed fields: dimensions, fill/text colors, radius, borders, font family/size/weight, line height, letter spacing and opacity. Each observed field retains its `value` and original `evidence`; `missing` and `conflicts` remain explicit. `parsed` means some properties with a unique layer name were recognized, not that all styles or business completion were verified.

Pass a known inspector CSS selector such as `{ "region": "#properties" }`, with the existing optional `frame` for an iframe. Omitting `region` reads bounded page text. The parser supports `label: value`, Chinese colons and adjacent label/value lines. Colors accept hex, `rgb/rgba` and HEX swatches with an alpha percentage, including bounded labelled color-style rows. Plain-color `background` and `background-color` are supported. Radii accept one to four values and normalize equivalent CSS shorthand while preserving evidence. Gradients and elliptical radii are unsupported. Unsupported layouts return `unrecognized` or missing fields; fall back to snapshots for inspection. Missing layer identity, conflicting or unsupported values make recognized results `partial`; affected properties are withheld and multiple layers are not merged. Truncated text returns `content-truncated` and requires a smaller region.

Inspector font names are retained as `fontFace`, separately from CSS `fontFamily`. Color alpha remains separate from layer `opacity`. Names such as Medium never substitute for an explicitly observed `fontWeight`.

Equivalent supported forms share their evidence, such as `#fff` and `rgb(255, 255, 255)`, or opacity `50%` and `0.5`. Different values still conflict. Recognized fields that are all withheld produce `partial`, requiring a narrower region or selection check; `unrecognized` means no supported properties were recognized.

Read background and text separately. This does not recover hidden layers, infer font weight from names, assume `px` for bare numbers or generate/merge CSS. The Host helper reuses `browser_get_text`, retaining page authorization, sharing, approval, session and cancellation checks without a new wire action. The matching extension preserves text line breaks; restart the Host and reload the extension after updating. Older extensions may flatten labels beyond recognition. See the [tool](src/tools.ts) and [parser](src/design-inspector.ts). `node scripts/smoke-visual.mjs` has passed synthetic field reads, design switching and native revocation checks. `STRIDE_REAL_MODEL=1` has verified that the existing default model uses the new helper for both layers and reports exact metrics. On 2026-11-04, the default model also completed exact background/text reads on a real Lanhu page in the user's regular Chrome, using five requests and nine browser calls after the view was enlarged. This covers that inspected design and interface, not general Lanhu layouts or automatic zoom.

Structured styles do not prove layout fidelity. Check selector matches and actual rendered margins, padding and gaps when editing a generated page. Unmeasured spacing remains unknown and existing values should be preserved, not reset to zero; `:first-of-type` counts element types rather than class matches.

## Preparing small design views

`browser_set_design_zoom` accepts `percent` (100–200) and optional `frame`. It supports a uniquely labelled native zoom select and the observed Lanhu detailDetach toolbar/menu. The Lanhu page must be in the foreground and offer the exact preset (100%, 150%, 200%); there is no rounding or canvas/CSS/browser-zoom fallback. Menu opening and selection use two private extension dispatches under the original logical tool call, with a fresh authorization/document check before selection and a single-use, expiring DOM pin. That pin is not authorization and is never forwarded to the Host or page world. Cancellation, revocation, navigation or a changed menu stops the second step; a lost selection receiver cannot replay the opening. The selected percentage is read back, then a fresh screenshot is required. Failed preparation fences that Agent's remaining browser calls until a new user turn; other Agents are unaffected. Both peers retain optional wire-v4 `designViewZoom`. See [supported layout and separate acceptance checks](../../../extensions/dsh-browser/README.md#canvas-and-design-pages).

## Measuring rendered layout

`browser_measure_layout` reads a unique rendered DOM element and an optional unique reference in the selected frame:

```json
{ "selector": ".customer-card", "referenceSelector": ".hero" }
```

The report separates viewport bounding boxes from computed CSS margins, padding, border widths and gaps. `comparison.verticalGap` measures the edge distance only when boxes overlap horizontally and are vertically separated or touching; `horizontalGap` is analogous. Overlapping or unaligned boxes return `null` for that gap, never an invented zero. Contained-box insets include the reference border and are not automatically padding. For example, `.card:first-of-type` may match nothing when a preceding `.hero` is also a `section`; this tool refuses that selector instead of claiming a measurement. Measuring `.customer-card` against `.hero` can then show the actual zero gap despite the stylesheet declaring a 50px rule for the wrong selector.

Each selector must match exactly one element (up to 500 characters). Missing, ambiguous, invalid or unrendered selections fail. `visibility:hidden` and opacity-zero elements still have measurable layout boxes and are identified in the report. Coordinates use CSS pixels in the current frame viewport; scroll offsets, device pixel ratio, transforms and fragment count are supplied for interpretation. This does not scroll, focus, change styles, read input values, pierce shadow roots or recover layers inside canvas images. Inline fragments, transforms, overlapping elements and dynamic layout require care; an observation is not a layout lock or a visual-fidelity verdict.

Both peers must negotiate optional wire-v4 `layoutMetrics`; restart the updated Host and reload the extension. An older peer remains compatible with existing tools but layout measurement returns update guidance. Existing page grants, selected-frame sharing, read approval, session/document/control fences and cancellation still apply. The JSON is enclosed in the untrusted page-content boundary. If the sharing budget is too small, the tool fails instead of returning partial JSON.

Build first, then run `pnpm run test:smoke-layout` for the isolated Host/Chrome synthetic fixture. Optional `STRIDE_REAL_MODEL=1` uses the existing default model, with the same private model patch/credential inputs as the visual smoke. Test homes and ports are isolated from the regular Host; results stay in ignored private storage. This does not test automatic design zoom or hidden Lanhu layer measurements.

## Configuration

For first connection, click **Connect to local DSH** in extension settings, then confirm the matching code in the signed-in DSH **Settings → General → Browser pairing** section. Up to eight requests stay in memory for five minutes; only a Connection-authenticated owner can approve them. Request proofs and installation credentials never enter Host pages or URLs. Credentials can be claimed once; lost responses, restart or storage failure require a fresh confirmation. Manual pairing codes remain supported. Normal source upgrades preserve pairing when the original extension installation and Host data remain; see the repository README for update steps.

| Key | Default | Meaning |
| --- | --- | --- |
| `token` | generated | Administrator token for pairing; if unset, the Host stores it in `DSH_HOME/ext-bridge-token` with restricted permissions. It is not a browser credential and is not logged. |
| `allowHostManagement` | `false` | Separate Host-side opt-in for settings, credentials and local-path gateway methods. A browser connection alone does not grant these permissions. |
| `pairingProfile` | `web` | Namespace for installation credentials under `DSH_HOME/browser-bridge-pairings` and the browser-run storage domain. Only one Host process may own a storage root/namespace at a time. |
| `toolTimeoutMs` | `90000` | Per-tool timeout in milliseconds. |
| `snapshotMaxChars` | `32000` | Snapshot character limit; minimum 500. |
| `maxInteractiveItems` | `60` | Maximum interactive items per snapshot. |
| `sessionWorkspacePath` | `DSH_HOME/browser-sessions` | Workspace for extension-created sessions; an empty string disables grouping. |
| `deferSessionCreate` | `true` | Materialize a new session when the first prompt is sent. |

`/ext/bridge-config` exposes only the local WebSocket address. Pairing administration is loopback-only, requires the separate administrator token and rejects browser Origin headers. A one-time code expires after five minutes; only a hash of the resulting installation credential is persisted by the Host. See the root README for issue/list/revoke commands. Extension credentials use extension-origin IndexedDB, including on Firefox where `storage.local` access cannot be restricted.

The shared [wire protocol](src/protocol.ts) is distinct from the [execution contract types](src/contracts/). The Host provides `ctx.browserRuns` for trusted plugins: queued run creation, version-checked state changes, pause/resume/stop, immutable action facts, and completion checks against declared criteria. Facts must be supplied by trusted Host code; tool success text is not verified evidence. Browser tools use its child dispatch ledger and explicit Host execution contexts. The panel reads metadata and controls existing runs, including selected-page continuation for eligible paused runs; creation and fact records remain Host-only.

Trusted Host code awaits browser work inside `withExecution(runId, controlRevision, async () => { /* await browser tools */ })`. The Bridge obtains the run, session and control revision from this async context, never from model arguments. Sessions with active or unreconciled runs cannot fall back to unscoped dispatch; unattributed calls cannot bypass an active run. Independent legacy sessions retain their existing behavior.

Pause, stop, resume, blocking, uncertain facts, storage faults and closure revoke old contexts. Resume requires a new context at the current revision. Old callbacks and detached children do not inherit fresh authority. Before browser dispatch, the extension uses `bridge.tool.confirm` to match the original pending request, action digest, session and run/control scope. The Host revalidates its captured execution object independently of the RPC async chain; copying ids cannot create a context. Confirmation is single-use and connection-owned. Cancellation revokes pending grants, including while approval is waiting; already dispatched effects remain uncertain. Account/tenant identification, general website business verification and automatic recovery remain unavailable.

The first confirmed managed page call pins an opaque extension-owned tab/binding id for its run/control revision. Later calls carry that expected id in the command digest and must match the same live native binding. A same-tab navigation can continue, while rebinding, tab lifetime/window changes and connection replacement fence the old pin. The Host keeps the connection owner across socket replacement; the worker refuses to reconstruct a missing expected id after restart. Selected-page continuation reserves a fresh target before the new running revision is published. That document must stay current until its first successful execution confirmation, after which normal same-tab navigation is supported. Both caches are process-local and bounded to 5,000 entries, with no automatic eviction. This is tab binding, not account/tenant identification. Managed open/follow/close tools remain refused before dispatch recording; only explicit user page binding and continuation can hand off a paused run.

Pending writes block starting, resuming or entering a new execution scope. Unresolved writes and failed write receipts also block further dispatch: failure can occur after a partial effect. A late successful receipt settles transport uncertainty without reviving old contexts or proving business success. There is no automatic reconciliation path yet.

The service requires DSH `storageDomain`, using domain `browser_runs_<UTF-8 hex of pairingProfile>` and the configured storage backend. The default JSON backend writes private files atomically; it does not coordinate multiple Host processes sharing one storage root. On reopen, unfinished execution contexts are fenced by a new control revision, running records become blocked, and stopping records remain stopping. Such records cannot resume until recovery support is implemented; no browser action is replayed. Raw run/fact RPCs and side-panel run deletion remain unavailable. Use the workspace checks in the root README and test real-browser behavior separately.

A storage-write failure disables subsequent writes until the domain is reopened. Unreconciled effects also block another run from starting in the same session. Each run accepts up to 128 distinct required criteria and 256 immutable facts. Stored state is a record, not permission to dispatch browser actions.

## Explicit browser tasks

When the DSH human-command service is present, `/browser <goal>` creates a queued task for the exact receiving Agent. It does not ask the model to decide whether to create a task. A waiting task starts only after a trusted extension startup action captures a native page and the Host reserves its pin before publishing `running`. **Bind and start** uses the selected authorized page. The command request signal does not own the durable task. The extension remains the place to select pages and control tasks; a separate DSH task dashboard and CLI/Desktop support are not implemented.

On Chrome, a queued task also offers **Open a new page and start** when the Host advertises `task.canStartNewPage`. The user enters a complete credential-free HTTP(S) URL and must have saved the automatic-page-control opt-in. Before creating a tab, the worker requests `bridge.browserTasks.preparePage` with the exact task/session/version/control revision and URL. Its single-use ticket belongs to that connection and expires after 45 seconds while unused. Creating, authorizing, grouping and binding the page shares the live write queue; the worker prepares its exact native pin before sending `bridge.browserTasks.start` with the ticket, launch URL and final target URL. Neither preparation nor page creation wakes the Agent. Generic panel RPC forwarding cannot call the preparation, cancellation or startup methods.

Confirmed pre-start failures release only this attempt's page authority and attempt to close its page, respecting native takeover; closure failure remains unconfirmed. Once the startup request is sent, a lost or uncertain reply preserves the page and pin and never causes a retry. A consumed ticket cannot be cancelled or reused. If startup remains uncertain while the task is still queued, further startup stays blocked; check the page and task, then explicitly stop the task before creating another. Reservations and pins are process-local, bounded to 5,000 entries and grant no recovery authority. The model still cannot open, follow or close tabs inside a managed run. Firefox retains selected-page startup. These optional methods and metadata keep wire v4 compatibility; build and reload both components to use the new flow.

The Host drives the existing Agent in a fresh `withExecution` scope. It exposes browser tools and the runtime's PTC transport, and denies unrelated registered tools. PTC programs retain the existing DSH Session sandbox policy for direct Node APIs; the registry restriction is not a separate filesystem or network sandbox. Known live Host parent tokens preserve original execution ownership across PTC callback boundaries; copied wire ids cannot create a child scope. Pause/stop revoke browser scopes and cancel the owned Agent activity. A stop is acknowledged only after it drains. DSH user cancellation stops the still-current task revision once its owned activity or verification exits; it cannot stop a later explicit continuation. Evidence committed before cancellation is retained without completing the task. New user input during an owned activity interrupts that task; conversational steering is not supported in this initial path. In-place goal edits and decreasing counters are rejected; use stop and a new task for a changed goal.

Initial limits are five active minutes, ten Agent model-request admissions including retries, and twenty browser invocations including PTC subcalls. Extension approval waits and user pauses do not consume active time, and continuation keeps previous counters. Existing per-tool timeouts still apply. These are initial guardrails, not measured performance promises. Limits stop further dispatch without replaying uncertain writes. Task records persist the user goal, monotonic counters and a fixed outcome code; dispatch records still omit raw arguments/results.

If any saved cumulative counter has reached its limit, the Host refuses startup or continuation with `budget-exhausted` before attaching a native target or changing the run's state. The panel removes startup/continuation controls and keeps stop available; stop the old task before creating another for remaining work. Pausing or changing pages does not reset limits. Already admitted activity may still finish trusted verification, so reaching a request/call count alone does not invalidate its result.

When the browser connection owning a task's native target closes, is replaced or is revoked, the Host immediately fences that exact run/control revision and cancels its active Agent scope. It then saves a pause with `pauseReason: 'browser-disconnected'`, preserving counters and action facts. The fence also covers connection loss during the initial target/start commit. A late event from the old connection cannot pause a successor revision. Ordinary unscoped chat and custom non-task executors keep their existing lifecycle.

Reconnecting the transport does not resume the task. Select its original conversation from history, check that the intended page is authorized and bound, then use **Continue on selected page**. The native handoff reserves a fresh revision; its Agent execution waits for the original activity to drain and retains cumulative budgets. Pending, unresolved or failed writes still prevent continuation; no action or uncertain write is automatically replayed. A Host restart still requires recovery and cannot use this path to restore an old page pin. The pause reason is optional wire-v4 metadata; older panels show their generic paused message. If another client replaced the connection, **Save and connect** explicitly reconnects with the existing settings; keepalive and policy-only saves do not take the connection back.

A continued task's current outcome returns to `pending`; its goal, counters and committed facts are preserved. Late verification from an older control revision cannot replace the current outcome with its earlier verdict. Verification time up to cancellation remains part of the cumulative active-time budget. The current activity still needs its own trusted verification result.

Normal Host shutdown is a retryable transport loss. While a side panel is open, the extension waits for the Host and reconnects using its saved credential; it does not need to be paired again. A connection replaced by another client still stops retrying until **Save and connect** or another explicit connection action. Task execution and native pins stay revoked, and Host restart recovery remains unimplemented. Reconnection alone neither resumes a task nor replays an action.

When both peers negotiate `caps.taskTargetLoss`, the extension background reports lost native pins through `bridge.browserTasks.targetLost` with `{ runId, sessionId, controlRevision, targetBinding }`. Revoking page control, closing the tab or invalidating its binding fences that original revision and pauses it with `pauseReason: 'page-unavailable'`; confirmed notification keeps the browser connected. Authorizing a page again does not resume the task. Pending or uncertain writes still block explicit continuation, and already-started page actions are not undone.

The Host checks the exact connection, session, revision and pin before pausing. Connection-owned revocation records also reject a matching native startup/handoff if loss arrives before its target commits. These records are bounded to 5,000 per connection; capacity exhaustion closes that connection rather than leaving a revocation unrecorded. Loss during an in-flight handoff fences its reserved future revision before publishing `running`. A stale pin cannot pause a successor. If a notification fails or its reply is unconfirmed, the worker closes only its original connection so the Host applies its disconnect fence; no browser action or notification is replayed through a successor. Older compatible peers omit this capability and the new pause-reason value, preserving generic paused metadata. Immediate page-loss pause requires both updated components.

Trusted Host code may call `ctx.browserTasks.registerVerifier(runId, { acceptsTarget, verify })` while the task is queued. The verifier must honor its cancellation signal and return independently obtained `ActionEvidence`, or `undefined` when the goal is not verified. It cannot be registered through model arguments, page content or browser RPC. The Host records verified criteria only from that evidence. An idle Agent or a success message is insufficient; without a verifier, after an uncertain write, or after a verifier error, the task remains blocked and needs verification. There is no automatic reconciliation or restart recovery. Controlled form fixtures live under `scripts/fixtures/`, outside the product runtime.

The opt-in `STRIDE_REAL_MODEL=1 pnpm run test:smoke-task` uses disposable Host/browser homes and a synthetic local form. `STRIDE_MODEL_PATCH` may name a private DSH model/preset patch; `STRIDE_MODEL_CREDENTIALS` may name a saved credentials file copied with private permissions into the temporary home and removed on exit. No saved user sessions or browser profiles are copied. This check invokes the authenticated DSH Web command endpoint and the real extension controls; it is not Desktop or CLI acceptance. Model outputs are not used as its result oracle.

Add `STRIDE_TASK_NEW_PAGE=1` to check native new-page startup with zero initial page grants. It checks refusal of synthetic clicks, a new debugger-controlled tab, its blue control group and exact session binding, run-bound tool receipts and independently saved fixture state. The fixture verifier uses a loopback address independently of Chromium's test-domain mapping.

`STRIDE_TASK_DISCONNECT=1` also uses new-page startup. A fixture holds the first completed snapshot, then a disposable authenticated peer replaces the isolated browser connection. The check confirms the paused reason, Agent quiescence, no business write and stable counters while disconnected/reconnected. Native **Save and connect**, history selection and **Continue on selected page** must precede any further model/browser work; a synthetic continuation click is refused. Both admitted revisions and independently saved synthetic state are checked. This is controlled connection-replacement acceptance, not evidence of automatic recovery or reconciliation of an uncertain write.

`STRIDE_TASK_TARGET_LOSS=1` uses a separate interruption scenario. After the first completed snapshot, it clicks the extension's native **Stop controlling this page** control and checks the page-loss pause reason, Agent quiescence, stable counters, revoked grant, an open page and a connected bridge. It then explicitly stops the task. The synthetic setting must remain unchanged throughout; this verifies interruption rather than completion of the business goal. Do not combine it with the disconnect scenario.

The separate `node scripts/smoke-host-reconnect.mjs` check uses disposable Host/browser homes without a model. It restarts the real Host on the same port, checks automatic reconnection and preserved pairing, and confirms a queued task remains idle. It then replaces the browser connection to confirm that case still requires native **Save and connect**. This is transport acceptance, not recovery of an interrupted task.

## Panel task controls

The authenticated browser connection handles `bridge.browserRuns.list` with `{ sessionId }` and `bridge.browserRuns.control` with `{ sessionId, runId, expectedVersion, control }`. Only `pause` and `stop` are accepted. The Host checks session ownership and the record version, and queued controls are cancelled with their original connection. These methods do not create tasks, grant browser permissions, record facts or resume work.

An optional `canRetarget` summary field enables **Continue on selected page** for paused runs without recovery requirements or pending, unresolved or failed writes. The user first selects an authorized group page above the conversation, then clicks the button. The worker checks the displayed binding revision and native target, generates an opaque pin, and calls `bridge.browserRuns.retarget` with `{ sessionId, runId, expectedVersion, controlRevision, targetBinding }`. Generic panel RPC forwarding cannot call this method. The Host checks ownership and versions and reserves the connection-owned pin before persisting `running`, advancing the control revision twice for `target_changed` and `resume`. Old contexts stay revoked; trusted Host code must enter a fresh `withExecution` context to continue. This does not start an executor or resume an ordinary chat automatically. An uncertain result only triggers a status refresh. The wire protocol remains v4; older compatible Hosts omit the capability and older panels ignore it.

The panel refreshes metadata every two seconds while open and connected. Responses contain at most 20 runs, unfinished first, with a total count; they omit criteria, facts, page evidence and arguments. A version conflict or uncertain reply triggers a state refresh, never an automatic command retry. `stopping` means the executor has not confirmed stopping yet. Ordinary chat sessions have no task card until trusted Host code creates a run. The normal chat cancel button still controls the Agent separately.

Selected-page startup and handoff errors retain their original error code and may add `targetState: 'unchanged' | 'uncertain'`. The Host declares `unchanged` only before entering target attachment and when that pin is not already known from an earlier attempt. The worker releases only its unused prepared pin before send or after this explicit refusal, so a later trusted click can prepare a fresh target. Once attachment is entered, or when a reply is lost or an older Host omits the field, it retains the pin and refreshes status without retrying. Releasing a prepared pin does not close the page or revoke its native access. Model/tool counter writes also recheck the original job after persistence before allowing their caller to proceed.

## Dispatch records

`ctx.browserRuns.dispatches` records every production `browser_*` dispatch, including calls without an Agent session. It uses a separate `browser_dispatches_<UTF-8 hex of pairingProfile>` domain. The Host commits request metadata and a digest before sending, then commits receipt metadata before returning the tool result. Cancellation, expiry and connection ownership are rechecked after each pre-dispatch write.

| State | Meaning |
| --- | --- |
| `prepared` | Request recorded; no dispatch marker committed. |
| `sent_unconfirmed` | Marker committed before socket send; actual delivery is unconfirmed. |
| `not_sent` | Host did not send, or restart found only a prepared record. |
| `unresolved` | Delivery or result is unknown after timeout, cancellation, disconnect or restart. |
| `returned` | Extension reply metadata recorded; this does not verify a business result. |

Records contain Host action/request/connection ids, optional installation/session ids and paired run/control-revision metadata, tool name, read/write classification, a SHA-256 request digest, timestamps and fixed status/error codes. Raw arguments, input values, page results and peer error messages are omitted. Read/write classification is shared with the extension; unknown tools count as writes. A storage failure stops subsequent ledger writes and dispatches until reopen. A late reply on the same connection can update an unresolved record while preserving its interruption; it does not revive the old caller. No action is automatically retried or replayed.

Permanent session purge removes its settled dispatch records after session storage deletion; unfinished runs and active dispatches block that operation. Unscoped records have no automatic expiry. Task-state/fact records retain their separate lifecycle.

Wire protocol v4 carries `{ actionId, requestDigest }` and an explicit execution scope. New ledger rows use `identityVersion: 4`: the command digest binds action id, tool name, arguments, optional session id and legacy/run scope, including run id/control revision and any previously confirmed target binding. `transportDigest` separately binds the original transport metadata. Confirmation cannot be reused after cancellation, context exit or connection replacement. Historical v2/v3 and transport-only rows remain readable audit data and are never upgraded into replayable requests. Build and reload both components together; older binaries may reject v4 ledger rows.

The extension commits an IndexedDB execution fence before entering the existing approval/target/write-queue flow. Repeated ids are refused, including after worker restart; changed command digests are conflicts. Only identity, timestamps and admission/finish phase are retained. A finish marker does not establish delivery or business success, and no stored page result is returned for a duplicate. The 5,000-record store has no automatic eviction, so a full or unavailable store refuses new execution, and a corrupt matching fence refuses its action. Host session deletion does not remove these replay fences. Account/tenant identification and automatic reconciliation remain unimplemented; execution confirmation does not bypass browser permissions.
